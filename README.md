# RoadGuard AI — Traffic Safety Intelligence Dashboard

An explainable AI-powered accident risk prediction and hotspot analysis
prototype, built as a single integrated Streamlit application.

---

## STEP 1 — Dataset Analysis

Source file: `data/accidents.csv`

| Property | Value |
|---|---|
| Rows | 20,000 |
| Columns | 24 |
| Duplicate rows | 0 |
| Duplicate `accident_id` | 0 |
| Missing values | Only `festival` (19,885 of 20,000 are missing — i.e. "no festival that day", not bad data) |

**Columns:** `accident_id, city, state, latitude, longitude, date, time, hour,
day_of_week, is_weekend, road_type, lanes, traffic_signal, weather,
visibility, temperature, traffic_density, cause, accident_severity,
vehicles_involved, casualties, is_peak_hour, festival, risk_score`

**Numerical:** `latitude, longitude, hour, lanes, traffic_signal, temperature,
is_weekend, is_peak_hour, vehicles_involved, casualties, risk_score`

**Categorical:** `city, state, road_type, weather, visibility,
traffic_density, cause, accident_severity, day_of_week, festival`

**Target candidate:** `risk_score` — a continuous value from 0.10 to 1.00
(18 discrete steps), which we rescale to a **0–100 scale**
(`risk_score_100`) for the whole app.

### Data leakage analysis (important finding)

We tested two models on identical train/test splits:

| Model | Features | R² | MAE |
|---|---|---|---|
| Pre-event only | hour, day_of_week, is_weekend, is_peak_hour, road_type, lanes, traffic_signal, weather, visibility, temperature, traffic_density | **0.876** | 0.056 (0-1 scale) |
| + `casualties`, `vehicles_involved`, `accident_severity`, `cause` | same as above + those 4 | **0.998** | 0.0015 |

The near-perfect R² of 0.998 when post-accident outcome columns are
included confirms `risk_score` is heavily derived from those columns in
this dataset. **Those 4 columns are excluded from the model** — they are
only knowable *after* an accident happens, so using them would make the
"risk prediction" meaningless in a real preventive-safety setting (you
can't know the casualty count of an accident before it happens).

The final model uses only pre-event features:
`hour, day_of_week, is_weekend, is_peak_hour, road_type, lanes,
traffic_signal, weather, visibility, temperature, traffic_density,
city, state, latitude, longitude, has_festival` (derived from `festival`).

`cause` and `accident_severity` are still shown in the **Analytics**
page as historical/descriptive charts — that's safe because it's
retrospective reporting, not a live prediction input.

### Risk thresholds

```
0–24    LOW       🟢
25–49   MEDIUM    🟡
50–74   HIGH      🟠
75–100  CRITICAL  🔴
```

Checked against the data: this split produces a reasonable spread
(≈16% LOW, 52% MEDIUM, 22% HIGH, 10% CRITICAL), so the requested
thresholds were kept as-is rather than replaced.

## STEP 2 — Final Architecture

```
CSV (data/accidents.csv)
    │
    ▼
engineer_features()  — derive has_festival, hour_bucket, risk_score_100
    │
    ▼
ColumnTransformer (OneHotEncoder + passthrough)  →  RandomForestRegressor
    │                                                        │
    ▼                                                        ▼
models/preprocessor.pkl                            models/trained_model.pkl
    │
    ▼
predict_risk_score(df) → 0-100 risk score  ──┬─→ Predict Risk page
                                              ├─→ Hotspot Map (scores + KMeans clusters)
                                              ├─→ SHAP explain_prediction()
                                              └─→ recommendations_for() (rule-based)
```

One Streamlit app (`app.py`), one shared model, one shared dataset — every
page reads from the same trained artifacts, so numbers are consistent
everywhere in the dashboard.

**Hotspots** — the dataset has no official zone/ward column, so we do
**not** invent one. Instead, `src/data_utils.build_hotspots()` clusters
each city's accidents by (lat, lon) with KMeans (up to 3 clusters per
city, fewer for small cities), producing labels like
`"Chennai - Cluster 1"`. This is clearly a coordinate-based grouping,
not an administrative zone.

## VANET Safety Network (simulated)

A new page — **VANET Safety Network** — demonstrates how a Vehicular Ad-hoc
Network layer could feed into RoadGuard AI. This is a **software
simulation**, not real hardware or live traffic data. Pipeline:

```
Simulated Vehicles → V2V → Roadside Unit (RSU) → V2I →
RoadGuard AI (existing trained model, on-demand inference) →
Hotspot Correlation → Safety Attention Alert
```

What's simulated vs. real:
- **Simulated:** vehicle positions/speeds/events, RSU event counts, V2V messages, timestamps
- **Real:** hotspot locations and historical risk (from `models/hotspots.csv`), city coordinates, the trained `RandomForestRegressor` (called once per alert for live re-scoring — never retrained), and the existing rule-based recommendation engine

The correlation logic (`src/vanet_utils.py: generate_safety_alerts()`) finds
the real hotspot geographically nearest to wherever simulated vehicles
reported a dangerous event, and only raises a Safety Attention Alert when
that hotspot is close enough (≤8 km) and enough dangerous events were
reported (≥2) — it does not fabricate alerts unconditionally.

## STEP 4 — Run Instructions (VS Code / local)

```bash
# 1. Unzip and open the RoadGuard-AI folder in VS Code
cd RoadGuard-AI

# 2. (Recommended) create a virtual environment
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

# 3. Install dependencies
pip install -r requirements.txt

# 4. Run the app
streamlit run app.py
```

A trained model and hotspot file are **already included** in `models/`,
so the app opens instantly. If you delete the `models/` folder (or run
on a different CSV), `app.py` will automatically retrain on first
launch — no extra steps needed. You can also train manually:

```bash
python train_model.py
```

**Login screen:** any email/password works — it's a demo login for the
hackathon, not real authentication.

## STEP 5 — Model Evaluation

Regression task (target: `risk_score_100`, 0–100 scale).

| Metric | Value |
|---|---|
| R² (held-out test set) | **0.887** |
| MAE | **5.17** points |
| RMSE | **7.23** points |
| Train / Test split | 16,000 / 4,000 (80/20) |

These numbers are visible live in the app sidebar under **📐 Model
Evaluation**, and are recomputed whenever the model is retrained — they
are never hard-coded in the UI.

Global feature importance confirms the leakage analysis: **visibility**
and **traffic_density** dominate the pre-event model (~80% of total
importance combined), with **is_peak_hour**, **weather**, and location
contributing the rest. `road_type`, `lanes`, and `day_of_week` have only
minor influence in this dataset.

## STEP 7 — Troubleshooting

| Problem | Fix |
|---|---|
| `ModuleNotFoundError: No module named 'streamlit'` (or folium/plotly/shap) | Run `pip install -r requirements.txt` again inside your active virtual environment |
| App is slow / hangs on first launch | That's the automatic model training step (only happens if `models/` is missing/deleted) — wait ~10-20 seconds, it only happens once |
| `FileNotFoundError` for `data/accidents.csv` | Make sure you're running `streamlit run app.py` from inside the `RoadGuard-AI/` folder, and that `data/accidents.csv` wasn't renamed/moved |
| Map doesn't render, or shows "API key required" watermarks | Confirm `folium` and `streamlit-folium` installed correctly (`pip show streamlit-folium`). The map uses an explicit, no-key CARTO Positron tile URL instead of folium's `"cartodbpositron"` alias, which on some folium versions resolves to a tile provider that requires a key |
| SHAP panel shows a fallback chart instead of SHAP bars | `shap` isn't installed — run `pip install shap`. The app degrades gracefully rather than crashing, so this is not a bug, just a missing optional dependency |
| Port already in use | Run `streamlit run app.py --server.port 8502` (or any free port) |
| Priority Score looks similar to Model Risk Score | Expected on a fairly uniform synthetic dataset — check the Hotspot Intelligence caption for the exact formula/weights; they're independent, documented, and not meant to always disagree, only to *account for* volume/peak-hour concentration in addition to model risk |

## Notes on scope / what's real vs. estimated

- All risk scores, SHAP values, feature importances, hotspot statistics,
  priority scores, alerts, and system insights are computed live from the
  actual dataset and trained model — **nothing in the dashboard is a
  hard-coded placeholder number.**
- "Predicted Accident Probability" was intentionally **not** added as a
  separate metric — the model is a risk-score regressor, not a
  probability-calibrated classifier, so a fabricated probability would
  be misleading. Risk Score (0-100) is the single, honestly-labeled
  output.
- The What-If Simulator and time-based charts are clearly labeled as
  **model-based estimates**, not guarantees of real-world outcomes.
- **Trend analysis was deliberately not added.** The dataset's dates
  (Jan 2022–Apr 2025) show essentially flat year-over-year accident
  counts (6,117 → 6,088 → 6,061, under 1% variation) and near-constant
  monthly average risk scores (std of 0.009 against a mean of 0.44) —
  there is no statistically meaningful increasing/decreasing signal to
  report, so no trend indicator is shown rather than fabricating one.
- **"Road Safety Attention Priority"** (shown on Command Center and
  Hotspot Intelligence) is a transparent, documented heuristic —
  50% normalized model risk score + 30% normalized historical accident
  count + 20% peak-hour accident share (see `compute_priority_score()`
  in `src/data_utils.py`) — explicitly distinct from, and not a
  substitute for, the Random Forest's model risk score.
- **Algorithm labeling:** the app consistently distinguishes K-Means
  (geographic clustering), Random Forest (risk-score prediction), SHAP
  (explaining the Random Forest's predictions), and the rule-based
  recommendation engine (not machine-learned) — never lumped together
  as "the AI model."
